# AvitoTask
solution for avito task
## 1. Пайплайн

1. Загружаем train и benchmark данные.
2. Подготавливаем тексты запросов и объявлений.
3. Для каждого запроса получаем кандидатов через:
   - BM25;
   - TF-IDF;
   - E5 dense retrieval.
4. Объединяем кандидатов из всех каналов без дублей в отдельный пул.
5. Для каждого кандидата считаем признаки.
6. CatBoostRanker переупорядочивает кандидатов внутри пула.
7. Берем top-50 объявлений для каждого запроса.

## 2. Используемые признаки

Из исходных данных использовались следующие поля:

- `search_query` 
- `search_infm_params_text` 
- `search_location_id` 
- `search_is_delivery_search`

- `item_title_raw` 
- `item_infm_params_text`
- `item_description_raw` 
- `item_location_id`
- `item_rating`
- `item_rating_reviews_count` 

Текстовые поля использовались для BM25, TF-IDF и E5 retrieval.
Локация использовалась как отдельный признак для CatBoost. Для запросов с доставкой ее влияние отключалось.
Рейтинг и количество отзывов были объединены в один признак `quality`.
Дополнительно проверялись, но не вошли в финальное решение:

- `item_price` — не дал стабильного улучшения Recall@50, вероятно больше нужен для финального ранжирования, нежели для генерации пула кандидатов;
- `item_is_phone_hidden` и `item_is_message_forbidden` — стабильного улучшения также не дали;
- `item_microcat_id` — ухудшал качество на локальной validation;
- `item_latitude` и `item_longitude` не использовались, так как в данных запроса нет координат пользователя, с которыми можно было бы взаимодействовать.

## 3. Алгоритмы и модели
Для генерации кандидатов использовались:
- BM25 — функция ранжирования документов по релевантности текстовому запросу;
- TF-IDF — способ векторизации текста с весами слов по их частоте и редкости;
- multilingual E5 — модель для получения семантических эмбеддингов текста;
- FAISS — библиотека для поиска ближайших векторов по эмбеддингам.
- CatBoostRanker - ранкер на основе решающих деревьев

## 4. Проверка качества
Train делился по уникальным запросам, поэтому один и тот же `query_uid` не мог одновременно попасть в train и validation.
На validation кандидаты формировались только retrieval-моделями. Известные правильные объявления специально в список кандидатов не добавлялись. 
Поэтому Recall@pool показывает, какую долю правильных объявлений удалось найти на первом этапе генерации кандидатов.

## 5. Основные эксперименты, выводы и ошибки
Основной тип ошибки candidate generation — релевантное объявление не попадало в пул. Для этого были объединены несколько retrieval-каналов и увеличен размер пула.
1. Увеличение и перераспределение размера retrieval pool заметно улучшило качество.
2. Наибольший уникальный вклад в candidate pool давал dense E5 retrieval. Среди lexical-каналов наиболее полезным оказался BM25 по объединенному тексту.
3. Локация оказалась одним из самых важных признаков ranker: удаление этого признака сильно ухудшало Recall@50.
4. `microcat`, цена и флаги доступности контактов стабильного улучшения не дали и были исключены.
5. Подбор гиперпараметров CatBoost через Optuna почти не изменил качество, поэтому дальнейший тюнинг модели оказался менее полезен, чем улучшение candidate generation.
